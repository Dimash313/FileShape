# FileShape — Telegram bot product roadmap (approved 2026-11-13)

Status: **approved product scope, not implemented**. This roadmap extends, rather than replaces, the technical release gates in [ROAD_TO_5.md](ROAD_TO_5.md). Work in separate branches and PRs, never merge with failing CI. Do not expose production or enable billing until separately validated. Preserve existing conversions, ownership, retention, safety and Mini App behavior.

## Product principles
- Premium, minimalist **black/white/graphite** identity across bot and Mini App; no blue, music or decorative living-being imagery.
- Telegram bot home: **one 16:9 graphic preview** as the message photo, concise independent caption, and logically grouped inline navigation keyboard. Graphic is branding/infographic only where it adds value (home and optional Premium introduction); **no graphic for every operation/status**. No fake live status/progress or sample analytics in production.
- Bot navigation should edit existing menu message where practical; avoid chat spam; clear back/home actions. Follow actual Bot API constraints on captions and button appearance. Bot already offers file-type actions; enhance, do not duplicate/break them.
- Premium and partner marketing must not compromise safe processing, privacy or usability of the Free tier.

## Delivery sequence (each separately scoped and gated)
1. **Access and entitlements foundation.** Audit aiogram/FastAPI/Mini App ownership boundaries and existing size/resource constraints. Implement owner-scoped durable user/entitlement records and safe migrations; admin role authorization; server-side entitlement check on *all* processing entry points, including bot, Mini App, direct API and retries. Design testable check policy with explicit failure behavior. No paid checkout yet.
2. **Required-channel gate and admin control.** Owner manually registers Telegram channel ID, invite link/display name, partner attribution, enabled flag, start/end times; bot verifies it has sufficient channel admin access. Verify individual user membership using Telegram Bot API `getChatMember`; no claim of access to complete member lists. Validate membership before accepting a new processing job, not merely in UI; never block an already accepted job or its owned result download due to later channel changes. Missing admin rights/API errors must not be silently treated as verified membership; expose an actionable failure. Free users only; Premium bypasses subscription requirement. Recommend at most three simultaneously required channels including the main channel. Admin controls and audit log for changes.
3. **Free quota and Premium policy.** Initial proposal: Free 5 **successfully completed** operations/day, 20 MiB per bot input where the Bot API permits, 3-file batch max; Premium no *daily operation-count* quota, up to 100 MiB only on transports that actually support it, up to 8-file batches only after each tool and deployment are validated, and queue priority within proven capacity. Technical per-user concurrency, CPU/time/disk/byte, rate and abuse limits remain on **both** tiers; no claim of unlimited resources. Keep current stricter limits until safely expanded. Use UTC day boundaries and atomic reservation/settlement; rejected/failed/cancelled/idempotent retries must not double-charge. Set actual pricing only after measured cost review.
4. **Telegram Stars checkout.** Proposed manual non-renewing durations: 1 day 15 Stars, 7 days 49 Stars, 30 days 149 Stars, 90 days 399 Stars. Confirm Telegram rules and price feasibility before activation. Secure invoice/pre-checkout and verified successful payment, deduplicated transaction ledger, idempotent grant, cumulative expiry, refunds/reversals, reconciliation and admin-only grants with audit. No external payment processor or recurring charge without approval.
5. **Referral rewards (time, not attempts).** Proposed cumulative one-time milestone bonuses for 1/3/5/10/25 verified invited users: +1/+3/+7/+14/+30 days Premium respectively; existing expiry extends. Qualifying referral must be a new unique user, pass required access gate and complete a genuine successful job. Enforce immutable attribution, no self-referral, anti-fraud and idempotent awards; avoid publishing identifying referral details. Admin-configurable future milestones without retroactive surprise awards.
6. **Owner-controlled partner placements.** **No self-service marketplace, no automatic advertising sales or automatic partner approval.** Owner alone negotiates and approves every channel/price/start/end; adds it manually in admin UI after confirming bot's membership-check rights. Scheduling automatically enables/disables only *owner-approved* placements. Campaigns may be owner-approved for a fixed **duration** or a target number of **confirmed joins** via campaign-specific bot-generated invite links, with an owner-defined maximum duration. Preserve a separate campaign ID/link for each placement, even on the same channel. Count a user at most once per campaign, deduplicate replayed membership updates, and stop automatically when the verified join target is reached. For valid counts, the bot needs channel-admin invite-link access and supported `chat_member` updates; Telegram does not provide universal link-open counts. Report join events, current verified membership, and observable departures as distinct metrics, never guarantee retention. Metrics: confirmed joins, known departures, membership checks and available impressions/taps, each explicitly labeled; do not misrepresent successful checks as new subscribers. Private files, filenames and user identities must not appear in partner analytics. Audit all changes; support pause, preview and manual termination.
7. **Admin panel and UX.** Owner/moderator/partner-scoped permissions (partner can see only approved aggregate metrics, if explicitly enabled), user search, access gates, active placements, referral milestones, Premium ledger, payment reconciliation, abuse/rate controls, tool toggles, announcement drafts, audit log. Admin identity must be server-side verified, never from a callback label or client claim. Sensitive changes require confirmation; preview channel gate/menu before publishing. Avoid mass messaging until rate/consent rules are designed.
8. **Bot navigation and quick actions.** Build 16:9 static graphic assets and separate copy/inline keyboard for the home navigator; concise tool categories, profile, Premium, referrals, help, Mini App. Detect incoming file type, validate size before download and show *only actually implemented* safe operations. Reuse existing conversion handlers and preserve private-chat owner isolation; do not extend file retention. Add favorites/recent tools only if scoped privacy requirements are satisfied.
9. **Release validation.** Python tests including concurrent entitlement updates, time-boundary/quota races, membership API errors, admin IDOR, forged callback, referral replay, payment duplication/refunds, channel expiry and owner isolation. Node/TypeScript/Vite and Docker builds; load and security audits; real Telegram bot/Android WebView and Stars sandbox scenarios. No production rollout or monetization claim until validated.

## Initial business rules and open gates
- Prices, file-size and batch expansion are **proposals** subject to real API transport and measured capacity; current runtime limitations take precedence.
- Premium bypasses daily count and required-channel marketing, **not** safety/resource limits.
- Main channel username/ID, owner Telegram ID and deployment bot permissions are configuration inputs, never hardcoded guesses.
- No user file contents in durable entitlement/payment/partner data. Retention, deletion, SQLite/WAL/symlink protections and least-privilege deployment continue to apply.
- Existing [ROAD_TO_5.md](ROAD_TO_5.md) security/load/release gates remain mandatory; product milestones may require additional versions. No rush to label 5.0 complete.
